# Data Model Specification: Bank Reconciliation Logic

**Feature**: 001-bank-reconciliation  
**Date**: 2026-06-23  
**Phase**: Phase 1 - Design & Contracts

## Overview

This document defines the core data entities and their relationships for implementing bank reconciliation logic. All data models align with the functional requirements and support deterministic reconciliation behavior.

---

## Core Entities

### 1. BankTransaction

**Purpose**: Represents individual transaction entry from bank statement PDF.

**Fields**:
```python
{
    "transaction_date": str,      # Format: "YYYY-MM-DD" (ISO 8601)
    "transaction_detail": str,    # Description of transaction
    "debit_credit": float        # Amount with sign: (-) for debit, (+) for credit
}
```

**Validation Rules**:
- `transaction_date`: Required, must be valid date string
- `transaction_detail`: Required, can be empty string, max length 500 chars
- `debit_credit`: Required, must be numeric, can be positive or negative

**Source**: Generated by `pdf_service.py` from PDF bank statement

**Examples**:
```python
# Credit transaction (money coming in)
{
    "transaction_date": "2026-05-05",
    "transaction_detail": "INWARD CHEQUE",
    "debit_credit": 10200.0
}

# Debit transaction (money going out)  
{
    "transaction_date": "2026-05-06",
    "transaction_detail": "P2P RECEIVING VIA GREAVES",
    "debit_credit": -22000000.0
}
```

### 2. CompanyTransaction

**Purpose**: Represents individual transaction entry from company financial records Excel.

**Fields**:
```python
{
    "transaction_date": str,      # Format: "YYYY-MM-DD" (ISO 8601)
    "transaction_detail": str,    # Description of transaction
    "debit_credit": float        # Amount with sign: (-) for debit, (+) for credit
}
```

**Validation Rules**:
- `transaction_date`: Required, must be valid date string
- `transaction_detail`: Required, can be empty string, max length 500 chars
- `debit_credit`: Required, must be numeric, can be positive or negative

**Source**: Generated by `excel_service.py` from Excel company records

**Examples**:
```python
# Debit transaction (expense)
{
    "transaction_date": "2026-05-04",
    "transaction_detail": "Salaries IIAP mo Apr-26",
    "debit_credit": -17929400.0
}

# Credit transaction (income)
{
    "transaction_date": "2026-05-04",

    "debit_credit": 22000000.0
```

### 3. DiscrepancyTransaction

**Purpose**: Represents transaction present in one source but not the other, with source attribution.

**Fields**:
```python
{
    "transaction_date": str,      # Format: "YYYY-MM-DD" (ISO 8601)
    "transaction_detail": str,    # Description of transaction
    "debit_credit": float,        # Amount with sign: (-) for debit, (+) for credit
    "FROM": str                  # Source identifier: "Bank" or "Company"
}
```

**Validation Rules**:
- `transaction_date`: Required, inherited from source transaction
- `transaction_detail`: Required, inherited from source transaction
- `debit_credit`: Required, inherited from source transaction, must be numeric
- `FROM`: Required, must be exactly "Bank" or "Company" (case-sensitive)

**Source**: Generated by `reconciliation_service.py` during reconciliation process

**Examples**:
```python
# Bank-only discrepancy
{
    "transaction_date": "2026-05-06",
    "transaction_detail": "Payment Suzuki Azim Motors WHT 5.515",
    "debit_credit": -40771.695,
    "FROM": "Bank"
}

# Company-only discrepancy
{
    "transaction_date": "2026-05-06",
    "transaction_detail": "Payment Suzuki Azim Motors WHT 5.515", 
    "debit_credit": 6771.238,
    "FROM": "Company"
}
```

**Note**: Transaction date and detail are preserved for display purposes only - they do not affect matching logic.

### 4. ReconciliationSummary

**Purpose**: Provides summary statistics about the reconciliation process and results.

**Fields**:
```python
{
    "total_bank_transactions": int,           # Total transactions in bank statement
    "total_company_transactions": int,         # Total transactions in company records
    "total_discrepancies": int,                # Total discrepancies found
    "bank_only_discrepancies": int,            # Discrepancies only in bank statement
    "company_only_discrepancies": int,         # Discrepancies only in company records
    "opposite_pairs_removed": int,            # Number of opposite sign pairs removed
    "processing_duration_ms": int,             # Total reconciliation time in milliseconds
    "pdf_processing_time_ms": int,            # PDF processing time (existing)
    "excel_processing_time_ms": int,          # Excel processing time (existing)
    "concurrent_processing": bool              # Whether PDF/Excel were processed concurrently
}
```

**Validation Rules**:
- All count fields: Required, must be non-negative integers
- Time fields: Required, must be positive integers (milliseconds)
- `concurrent_processing`: Required, must be boolean

**Source**: Calculated by `reconciliation_service.py` and response helpers

**Example**:
```python
{
    "total_bank_transactions": 26,
    "total_company_transactions": 20,
    "total_discrepancies": 15,
    "bank_only_discrepancies": 8,
    "company_only_discrepancies": 7,
    "opposite_pairs_removed": 4,
    "processing_duration_ms": 7153,
    "pdf_processing_time_ms": 7151,
    "excel_processing_time_ms": 191,
    "concurrent_processing": True
}
```

### 5. ReconciliationResult

**Purpose**: Complete reconciliation response containing all processed data and discrepancy results.

**Fields**:
```python
{
    "request_id": str,                         # Unique request identifier (UUID)
    "processing_status": str,                  # Status: "completed", "partial", "error"
    "processing_timestamp": str,               # ISO 8601 timestamp
    "summary": ReconciliationSummary,         # Summary statistics (object)
    "results": {
        "bank_statement": List[BankTransaction],      # All bank transactions
        "company_records": List[CompanyTransaction],  # All company transactions  
        "discrepancies": List[DiscrepancyTransaction]  # Unified discrepancy list
    },
    "errors": List[str],                       # Error messages (if any)
    "message": str                            # User-friendly status message
}
```

**Validation Rules**:
- `request_id`: Required, must be valid UUID string
- `processing_status`: Required, must be "completed", "partial", or "error"
- `processing_timestamp`: Required, must be valid ISO 8601 timestamp
- `summary`: Required, must contain all summary fields
- `results`: Required, must contain all three transaction lists
- `errors`: Required, can be empty array
- `message`: Required, user-readable message

**Source**: Generated by route handler in `routes.py` combining all service outputs


## State Transitions

### Transaction Processing States

```
┌──────────────┐
│ Raw File     │
│ (PDF/Excel)  │
└──────┬───────┘
       │ parsed
       ▼
┌──────────────┐
│ Transaction  │
│ List         │
└──────┬───────┘
       │ reconciled
       ▼
┌──────────────┐
│ Discrepancy  │
│ List         │
└──────┬───────┘
       │ filtered
       ▼
┌──────────────┐
│ Final Result │
│ (with FROM)  │
└──────────────┘
```

### Reconciliation Process States

1. **Initial State**: Raw files uploaded
2. **Processing State**: Files parsed into transaction lists
3. **Comparison State**: Transactions compared for matches
4. **Filtering State**: Opposite sign pairs removed
5. **Final State**: Unified discrepancy list with source attribution

## Validation Constraints

### Business Rules

1. **Amount-Based Matching Only**: 
   - Transactions match if `bank_amount == -company_amount`
   - Date and description do NOT affect matching
   - Matching is case-sensitive for amounts

2. **Deterministic Behavior**:
   - Same inputs always produce same outputs
   - Transaction order preserved from sources
   - Opposite sign pairs removed consistently

3. **Source Attribution**:
   - Bank-only discrepancies get `FROM: "Bank"`
   - Company-only discrepancies get `FROM: "Company"`
   - No ambiguous source assignments

4. **Opposite Sign Removal**:
   - Pairs removed from both lists
   - One-to-one matching (first come, first served)
   - No partial matches or fuzzy logic

### Data Integrity Constraints

1. **Required Fields**: All entities require all defined fields (no nulls)
2. **Type Safety**: Amounts must be numeric, dates must be strings
3. **Range Constraints**: 
   - Counts must be non-negative
   - Times must be positive
   - Amounts can be any numeric value (positive, negative, zero)

## Error Handling

### Invalid Data States

1. **Empty Transaction Lists**:
   - Valid input (no transactions to reconcile)
   - Return empty discrepancy list with appropriate message

2. **Malformed Transactions**:
   - Missing required fields
   - Invalid data types
   - Return error and skip processing

3. **Processing Errors**:
   - Reconciliation service failures
   - Graceful degradation to raw transaction data
   - Clear error messages in response

### Error Response Structure

```python
{
    "request_id": "uuid",
    "processing_status": "error",
    "processing_timestamp": "ISO8601",
    "summary": {
        "total_bank_transactions": 0,
        "total_company_transactions": 0,
        "total_discrepancies": 0,
        "processing_duration_ms": 0
    },
    "results": {
        "bank_statement": [],
        "company_records": [],
        "discrepancies": []
    },
    "errors": [
        "Failed to process bank statement: Invalid PDF format",
        "Reconciliation service timeout"
    ],
    "message": "Processing failed - Please check error details"
}
```

## Performance Considerations

### Memory Management

- **Transaction Lists**: Keep in memory during processing only
- **Discrepancy Lists**: Stream generation, don't store intermediate copies
- **Result Assembly**: Build response incrementally

### Processing Efficiency

- **Nested Loops**: Acceptable for 500x500 = 250K comparisons (~50ms)
- **Early Termination**: Break loops when matches found
- **Order Preservation**: Maintain original transaction order

### Scalability Limits

- **Recommended**: 50-200 transactions per source (typical monthly statements)
- **Maximum**: 500 transactions per source (performance degraded but functional)
- **Beyond**: Implement pagination or batching (future enhancement)
