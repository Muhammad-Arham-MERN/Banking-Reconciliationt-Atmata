# Feature Specification: Admin Dashboard (Camri Desk)

**Feature Branch**: `008-admin-dashboard`  
**Created**: 2026-09-30  
**Status**: Draft  
**Input**: User description: "First of three specs for pushing the product to companies. This spec is Developer-only: a hidden admin dashboard (route 'AdminDashAccess') where I sign in with a username/password (validated against backend environment variables) and manage client companies — add, edit, delete, and view their status. Each company has a required name, optional logo file, an access password (randomly generated or manually entered), a price in Rupees, and a Payment Status (Pending / Free Trial / Paid) shown in the list. Companies live in a dedicated table; their passwords are encrypted at rest with a reversible symmetric encryption key held in the environment (decryption for company login comes in a later spec). Keep it simple and concise."

## Clarifications

### Session 2026-09-30

- Q: What are the Price semantics and precision (recurring vs one-time, whole vs decimal Rupees)? → A: Recurring per period, whole Rupees (integer). Storage and display only — no billing, invoicing, or charging logic is implemented in this specification; the Developer implements the price structure in a later specification.
- Q: How visible is the Company Password in the dashboard? → A: Masked in the list, revealable and copyable at any time, so the Developer can re-share credentials.
- Q: Who can change Payment Status in this specification? → A: New companies default to **Pending**; the Developer may change it from this dashboard, but the later company-facing dashboard is the primary manager of statuses.
- Q: How does the admin session end? → A: Browser-session only — the session expires when the browser is closed, after which the admin username and password are required again (no persistent "remember me").
- Q: What logo formats and size limits apply? → A: PNG, JPG, or SVG only; no additional size limit is imposed by this feature.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Sign in to the hidden admin dashboard (Priority: P1)

The Developer opens a private, unlisted route called **AdminDashAccess** — reachable only by typing the address directly, never through any link, menu, or button in the application — and signs in with an admin username and password. The credentials are checked against values configured in the backend environment; on success the Developer lands on the admin dashboard, and on failure access is denied.

**Why this priority**: Nothing else in this feature can be reached without it. It is the gate that keeps the management surface invisible and private.

**Independent Test**: Navigate directly to the AdminDashAccess route, submit wrong credentials (access denied), then submit the configured correct credentials (dashboard opens). Confirm the route is not referenced anywhere in the app's navigation.

**Acceptance Scenarios**:

1. **Given** the Developer is not signed in, **When** they open the AdminDashAccess route directly, **Then** they are shown a username and password form and cannot see any company data.
2. **Given** the correct admin username and password configured in the environment, **When** the Developer submits them, **Then** access to the admin dashboard is granted.
3. **Given** incorrect credentials, **When** the Developer submits them, **Then** access is denied with a generic message that does not reveal which field was wrong.
4. **Given** the AdminDashAccess route, **When** any page of the application is browsed, **Then** no link, menu entry, or button anywhere references or reveals it.
5. **Given** the Developer signed in and then closed the browser, **When** they reopen the AdminDashAccess route, **Then** they must sign in with the username and password again.

---

### User Story 2 - Register a new client company (Priority: P1)

After a deal is agreed with a company, the Developer opens the dashboard, clicks **"+ Add Companies"**, and fills a popup form: Company Name (required), Company Logo (optional file), Company Password (either generated by a random password generator or entered manually), and Price in Rupees. Saving the company makes it immediately appear in the companies list, ready for the Developer to hand the credentials to the company.

**Why this priority**: Creating a company account is the entire purpose of the dashboard — it is how a new client is onboarded.

**Independent Test**: From the dashboard, click "+ Add Companies", submit a company with only a name and price (no logo) and a generated password, and verify it appears in the list; repeat with a manual password and an uploaded logo.

**Acceptance Scenarios**:

1. **Given** the Developer is on the dashboard, **When** they click "+ Add Companies", **Then** a popup form opens with fields for Company Name, Company Logo (file), Company Password, and Price.
2. **Given** the add form, **When** Company Name is empty, **Then** the form does not submit and prompts for the required name.
3. **Given** the add form, **When** the Developer requests a generated password, **Then** a random password is filled into the password field and can still be edited manually.
4. **Given** a completed form, **When** the Developer saves, **Then** the company appears in the companies list immediately.
5. **Given** a company is created, **Then** its Payment Status is set to the default without any extra action from the Developer.

---

### User Story 3 - Manage and review registered companies (Priority: P2)

The Developer views all registered companies in a single table and, for any row, can review its details, edit them, or delete the company. Each row shows the company name and logo, its password (masked, with a reveal/copy action so the Developer can share it), the price in Rupees, and the Payment Status (Pending / Free Trial / Paid).

**Why this priority**: Day-to-day administration — updating prices, correcting details, revoking a client by deletion, and seeing payment state at a glance. Valuable once companies exist, so it follows creation.

**Independent Test**: With at least one company present, edit its name/price/status and confirm the row updates; then reveal its password and confirm it matches what was set; finally delete it and confirm it disappears from the list.

**Acceptance Scenarios**:

1. **Given** registered companies, **When** the Developer opens the dashboard, **Then** all of them are listed with name, logo, password (masked), price in Rupees, payment status, and row actions.
2. **Given** a company row, **When** the Developer edits its details and saves, **Then** the updated values are shown in the list.
3. **Given** a company row, **When** the Developer reveals its password, **Then** the original password set at creation is shown and can be copied.
4. **Given** a company row, **When** the Developer deletes it, **Then** the company is removed from the list and no longer has access.
5. **Given** a company with any payment status, **When** the list is shown, **Then** its status is displayed as one of Pending, Free Trial, or Paid.

---

### Edge Cases

- What happens when invalid admin credentials are submitted repeatedly? Access stays denied with a generic message; no account lockout is required for a single-Developer tool.
- What happens when a company name already exists? The system rejects the duplicate so that the company name stays unambiguous as the company's identifier.
- What happens when the encryption key is missing from the environment? The system refuses to store a company password and surfaces a clear configuration error rather than ever storing it in plain text.
- What happens when the logo file type is unsupported? Only PNG, JPG, and SVG are accepted; any other type is rejected with a message and the rest of the form is preserved. No additional size limit is imposed by this feature.
- What happens when the admin closes the browser? The session ends and the username and password are required again on the next visit to AdminDashAccess.
- What happens if the encryption key is lost or changed? Previously stored company passwords can no longer be decrypted — an accepted consequence of key loss.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The admin dashboard MUST live at a hidden route named `AdminDashAccess` that is not linked, listed, or referenced from any navigation, menu, page, or button in the application, and is reachable only by entering the address directly.
- **FR-002**: The route MUST require an admin username and password before any dashboard content is shown.
- **FR-003**: Admin credentials MUST be validated on the server against username and password values supplied by the backend environment; credentials MUST NOT be embedded in any client-delivered resource.
- **FR-004**: Invalid credentials MUST be rejected with a generic message that does not disclose which field was incorrect.
- **FR-005**: A successful sign-in MUST establish an admin-only session that is required for every company management action; the admin session MUST be independent of the normal application users and MUST end when the browser is closed, after which the admin username and password are required again (no persistent login).
- **FR-006**: The dashboard MUST be a single page that lists all registered companies.
- **FR-007**: Each listed company MUST display its Company Name, Company Logo, Company Password (masked by default, with a reveal and copy action), Price in Rupees, Payment Status, and per-row actions.
- **FR-008**: The dashboard MUST present a **"+ Add Companies"** control above the list that opens a popup dialog to create a company.
- **FR-009**: The create form MUST capture Company Name (required), Company Logo (optional file upload restricted to PNG, JPG, or SVG), Company Password (required, generated or manually entered), and Price in Rupees (required).
- **FR-010**: The create form MUST offer a random password generator and MUST allow the generated value to be edited or replaced manually.
- **FR-011**: The system MUST block creation when Company Name is empty.
- **FR-012**: The Developer MUST be able to edit any company's details, including its name, logo, password, price, and payment status.
- **FR-013**: The Developer MUST be able to delete a company; deleting a company MUST revoke that company's access.
- **FR-014**: Every company MUST have a Payment Status whose allowed values are **Pending**, **Free Trial**, and **Paid**; newly created companies MUST default to **Pending**. The Developer MAY change the status from this dashboard, but the later company-facing dashboard is the primary place where statuses are managed.
- **FR-015**: Price MUST be stored and displayed in Rupees as a whole-number (integer) amount representing a recurring per-period charge. No billing, invoicing, or charging logic is implemented in this specification — the price structure and charging are deferred to a later specification.
- **FR-016**: Companies MUST be persisted in a dedicated company table containing the name, logo, encrypted password, price, and payment status, and MUST survive application restarts.
- **FR-017**: Company passwords MUST be encrypted at rest using reversible symmetric encryption (Fernet) with an encryption key supplied by the backend environment; plain-text passwords MUST never be stored or written to logs.
- **FR-018**: The dashboard MUST be able to reveal a company's password on demand (decrypting with the same key) so the Developer can share it with the company; this on-demand reveal is distinct from the company-login decryption planned for a later specification.
- **FR-019**: The company name MUST serve as the company's identifier for the later company-facing sign-in; the company-facing login and dashboard are out of scope for this specification.
- **FR-020**: The dashboard list, create, edit, and delete operations MUST reflect changes immediately in the user interface after a successful save.

### Key Entities *(include if feature involves data)*

- **Admin Credential**: The single Developer-controlled account used to access the hidden dashboard — a username and password held in backend environment configuration; no self-service registration or password reset exists.
- **Company (client account)**: A registered organization the Developer has onboarded — Company Name (required, unique identifier), Company Logo (optional PNG/JPG/SVG file), Company Password (encrypted at rest), Price in Rupees (whole-number, recurring per period; stored only, not billed in this specification), and Payment Status (Pending / Free Trial / Paid; default Pending).
- **Company Credential**: The company's access password, encrypted with the environment-held symmetric key; used by the dashboard for reveal/copy now and by the company-facing sign-in in a later specification.

### Assumptions

- There is exactly one admin — the Developer — and credentials live in backend environment variables alongside the existing application configuration.
- The company name acts as the company's username for the later company-facing login; no separate username field is introduced in this specification.
- A newly created company's Payment Status defaults to **Pending**; the later company specification is the primary manager of statuses and will move them to Free Trial or Paid.
- The dashboard can reveal a company password on demand using the same reversible key; the "decryption in a later specification" refers to verifying company logins, not to hiding the value from the admin.
- Price is captured as data only — no billing, invoicing, or charging flow is built in this specification; the Developer implements the price structure in a later specification.
- The admin session is browser-session only — no "remember me" or persistent login; closing the browser requires signing in again.
- The company logo is optional and stored as uploaded; only PNG, JPG, and SVG are accepted, with no additional size limit imposed by this feature. When omitted, the list shows a placeholder.
- The company table is created alongside the existing database setup, consistent with how other application tables are provisioned.
- The admin session for this dashboard is independent and simpler than the existing end-user authentication; no third-party sign-in is involved for the admin.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A Developer entering correct credentials reaches the dashboard in under one minute, while 100% of attempts with incorrect credentials are denied access to any company data.
- **SC-002**: The AdminDashAccess route is undiscoverable through the application's interface — zero links, menu entries, or buttons reference it across every page.
- **SC-003**: A Developer can register a new company (with or without a logo, using a generated or manual password) in under two minutes, and the new company appears in the list immediately.
- **SC-004**: Inspecting stored data directly shows 0 company passwords in readable form — every stored password is unreadable without the encryption key.
- **SC-005**: A Developer can edit or delete any company, and 100% of changes are visible in the list immediately and remain after an application restart.
- **SC-006**: 100% of listed companies display a payment status, with newly created companies showing the default status without additional action.
- **SC-007**: The Developer can retrieve any company's original password on demand, and it matches the value that was set.
- **SC-008**: After the browser is closed and reopened, 100% of attempts to reach the dashboard require the admin username and password again — no session survives a browser restart.
- **SC-009**: 100% of accepted company logos are PNG, JPG, or SVG; every other file type is rejected, and no company record is created with an unsupported logo.
